# 对接生产机（v1.4.0）：把六段式送进立映，跑成片 + 队列并发与卡死诊断

> 本文件解决两件事：**① 写完的稿子怎么安全送进立映跑出成片；② 遇到「3 队列 vs 10 队列并发」「一直卡着不动」「怀疑卡审核或贴错素材」时怎么一分钟定位解决。**

---

## 生产机 v1.8.1 安全交接（优先于下文旧桥接流程）

实际投片使用新版 `h3pm enqueue/asset/watch`，不要混用旧桥脚本的 push/kick 与新清单身份管理。
- 交接保留清单中的 attempt、queueId、taskId、retries；queueId-only 表示等待派发，并非提交失败。
- 重复 enqueue/asset 默认恢复；用户明确要新版本才允许 `--rerun`，不要改名绕过未知提交。
- watch 精确绑定 queueId，不按同名猜任务。失败重试次数持久化，未知回执、上传失败、404、503 不盲投。
- 时间戳或进度冻结仅告警，不证明会话失效；禁止因此重启全部任务或清空队列。手动 revive 必须先获用户授权。

## 一、一次性准备（只做一次）

立映生产机要带调试端口启动，Agent 才连得上它的队列：

## 二、交付物三件套（Skill 产出，投喂前必须齐）

| 件 | 内容 | 谁用 |
|---|---|---|
| `段NN_时长_标题.txt` | **剥壳六段式纯文本**（字段名独立一行 + 空行 + 内容，不带 `**`、不带 ``` 围栏） | 直接进提示词框 |
| `图槽表.md` | Picture 1…9 → 文件名 + 各自锁什么（人物/场景/道具） | 挂图时照表挂 |
| `清单.json` | 每段的 name / file / duration / resolution / aspect / images[] | 桥脚本读 |

**剥壳是硬要求**：H3 会把提示词原样编码，`**subject_definitions**` 这种 Markdown 标记会变成正文的一部分。

清单格式（`images` 数组顺序 = 图槽顺序，**第 1 个元素就是 `Picture 1`**）：

```json
[
  {
    "name": "段01_15s_规矩",
    "file": "段01_15s_规矩.txt",
    "duration": "15",
    "resolution": "720P",
    "aspect": "9:16 (Portrait Widescreen)",
    "images": [
      "1_pic1_林昭.png",
      "2_pic2_老周.png",
      "3_pic3_出租屋门厅.png"
    ]
  }
]
```

## 二·补、出图（先出图，再投视频）

图也在生产机里出，**只用 `ZImage_通用生图_快出`**。别的出图工作流（Krea2 / Qwen）实测容易出黄色内容，一律停用。

- **角色三视图**：画幅 `4:3 (Standard)` + 分辨率 `2.0`，必须写「画面被两条竖线均分为恰好三格，从左到右依次排列：第一格正面全身、第二格侧面全身、第三格背面全身」。
- **场景单主视角**：画幅 `9:16 (Portrait Widescreen)` + 分辨率 `2.0`，只出一张正对空间的平视主视角，**禁九宫格、禁多视角拼图**（给多视角拼图会导致 H3 空间尺度膨胀）。
- **落盘命名铁律**：`素材库/人物|场景|道具/{slot}_{name}.png`，命名只认**槽位号**——它是唯一和 `<Picture N>` 对得上的东西。

## 三、3 队列 vs 10 队列：同时可以跑几个？排队可以排几个？

> **用户高频核心问题**：为什么有的号显示 3 队列、有的号是 10 队列？到底能同时跑几个、排队排几个？一次性投进去会不会卡死？

### 3.1 两层队列机制（服务端并发通道 vs 本地等待池）

立映生产机的队列分为**两层**，理解这两层就不会再把任务跑崩：

| 层级 | 决定什么 | 3 队列账号（基础/标准号） | 10 队列账号（高配/多通道号） |
|---|---|---|---|
| **① 服务端并发通道 (`concurrencyLimit`)** | **同时正在跑几个**（状态为 `dispatched` 读条中） | **最多同时跑 3 段**（或 1~2 段在跑 + 1~2 段服务端缓冲，合计占满 3 个通道） | **最多同时跑 10 段**（10 条服务端通道并行渲染） |
| **② 本地排队等待池 (`pending` 列表)** | **后面排队能排几个**（状态为 `pending` 0% 等待中） | **本地可排 10~20+ 段**（整集一次性 `push` 入队完全没问题） | **本地可排 10~30+ 段**（整集或多集一次性入队） |

**核心调度原理**：
- 当你把一整集 8 段任务 `push` 进立映时：
  - 如果是 **10 队列号**（`concurrencyLimit = 10`）：8 段会**全部同时变成 `dispatched` 开跑**，0 段排队；
  - 如果是 **3 队列号**（`concurrencyLimit = 3`）：只能让 **3 段变成 `dispatched` 同时跑**，剩下的 **5 段必须老老实实留在本地 `pending`（等待中）排队**！前序跑完 1 段（变成 `completed` 释放通道），客户端会自动从 `pending` 里补进 1 段，直到 8 段全部跑完。
- **为什么以前写死并发或盲目强推会卡死？**
  - 旧版 `v1.3.11` 把 `concurrencyLimit` 写死为 `4`：在 **10 队列号**上浪费了 6 条通道（产能砍掉 60%）；而在 **3 队列号**上，第 4 段被强行推给服务端，服务端因通道超限静默丢弃或挂起，导致本地客户端那第 4 段永远卡在 `dispatched` 假死！

### 3.2 怎么查我这个号是几队列？怎么手动控并发？

```bash
# 1. 查当前账号是 3 队列还是 10 队列（服务端下发实数 + 当前已占槽位）
node scripts/h3-bridge.js limit

# 2. 按账号容量自动派发（推荐默认）
node scripts/h3-bridge.js push 投喂包/清单.json

# 3. 手动压低并发（例如 3 队列号求稳、或同账号两台电脑共享通道时只用 2 条通道）
node scripts/h3-bridge.js push 投喂包/清单.json --limit 2
```

三级容量决议（`h3-bridge.js` 自动执行）：
1. **权威值**：读取服务端下发的 `snapshot().channelCheck.concurrencyLimit`（3 或 10），并自动扣除 `localOccupied / serverOccupied` 已占槽位；
2. **次选值**：若服务端未下发，从历史已完成任务的 `dispatchedAt ~ completedAt` 时间轴重叠度反推真实并发数；
3. **手工覆盖**：若传了 `--limit N`，取 `min(N, 服务端上限)`，绝不允许把 `--limit` 设得比服务端上限还高。

## 四、图槽铁律与「防贴错素材 / 防省图错位」自动拦截

> **真机血泪教训**：很多时候用户以为"卡审核了"或"怎么莫名多出一个人/换了间屋子"，其实是**省图导致槽位前移**或**人景贴反**！

1. **Picture 编号 = `images` 数组的第 N 张图（从 1 开始），绝不是资产名字里的数字！**
2. **全片槽位一次钉死，中间不用的图也必须挂上（严禁省图）**：
   - 反例（《门后》段02 差点踩的坑）：全片 `Picture 1 = 林昭`、`Picture 2 = 老周`、`Picture 3 = 门厅`。到了段02，老周没出场，正文只引用了 `<Subject 1> (Picture 1)` 和 `<Subject 3> (Picture 3)`。如果你在段02 的 `images` 里把老周删掉、只传 `[林昭.png, 门厅.png]` 两张图：
     - `门厅.png` 就会变成 `Picture 2`！
     - 而正文里的 `Picture 3` 变成了**空槽越界**！服务端要么直接卡死，要么把门厅当人画！
   - 正解：**全片所有段落的 `images` 数组保持完全相同长度和顺序**；段02 不用老周，正文不提 `<Subject 2>` 即可，但 `images[1]` 依然放 `2_pic2_老周.png` 占住 2 号槽！
3. **`h3-bridge.js` 现已内置自动防呆拦截**：
   - `push` 和 `doctor` 会自动读取 `.txt` 里的 `subject_definitions`，一旦发现正文最大 `Picture M` 大于 `images.length`（省图越界），或把场景图挂进了人物槽（贴错素材），**在入队前直接报错拦截**，绝不让错单进队列浪费算力。

## 五、入队、点火与一键诊断（标准四步）

```bash
# 1. 投喂前诊断（查图槽是否贴错/漏挂、查高危卡死动作、查敏感词、查队列僵尸）
node scripts/h3-bridge.js doctor 投喂包/清单.json

# 2. 整包入队（可加 --dry 先试跑，或加 --limit 3 限流）
node scripts/h3-bridge.js push 投喂包/清单.json

# 3. 让客户端用内部凭据点火认领队列
node scripts/h3-bridge.js kick

# 4. 看进度（实时显示：在跑 X/容量 C ｜ 本地排队 Y ｜ 完成 Z ｜ 失败 W）
node scripts/h3-bridge.js ls
```

## 六、出片之后：三关复检

```bash
# 1. 规格核对
ffprobe -v error -select_streams v:0 -show_entries stream=width,height,r_frame_rate \
        -show_entries format=duration -of default=nw=1 段01.mp4

# 2. 抽帧联络表（每秒一格，人眼查：门有没有提前开、有没有分身克隆人、有没有冻帧）
ffmpeg -y -i 段01.mp4 -vf "fps=1,scale=360:-1,tile=5x3" -frames:v 1 段01_联络表.jpg

# 3. 切点核对
ffmpeg -v error -i 段01.mp4 -vf "scdet=t=6,metadata=print:file=-" -f null - 2>&1 | grep -o 'lavfi.scd.time=[0-9.]*'
```
