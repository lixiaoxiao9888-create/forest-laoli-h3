## v2.0.2（2026-11-01）· 五轮自测循环修复（4 个真 bug）

v2.0.1 之后按「测试 → 打分 → 修 → 再测」跑了五轮。前两轮只测脚本，第三轮换成测文档与真实用法后，分数从 8.5 掉到 7.5——**掉分那轮才是真实水位**，下面 4 个 bug 就是那时暴露的。

### 一、按文档做出来的清单.json，机检根本读不了（**最严重**）

`delivery.md §三/§四` 明确让用户"把带 `images` 数组的载荷 JSON 喂给 `h3_lint.py` 才查得到 H36"，但 §四 给的清单格式是**数组**，而 `load()` 只认**单个对象**。照文档操作的结果是直接报错：

```
读取失败：'list' object has no attribute 'get'
```

文档指的路，工具走不通——比没有这个功能更糟，因为用户会以为是自己写错了。

- **修法**：`load()` 支持三种载荷——单对象、**清单数组**、纯文本。清单数组会自动去读同目录下 `file` 指向的剥壳 `.txt`，自动取条目里的 `aspect`，多段自动拼接后走切分器。
- **报错可读**：清单里一条都读不到时，明确说"确认 `file` 指向的 .txt 与清单在同一目录，或条目里直接带 `prompt` 字段"，并列出缺失的文件名。
- **画幅优先级**：`--aspect` > 载荷 `aspect/aspect_ratio` > 正文里扫。
- **新增用例**：`case28`（清单正例）、`case29`（清单省图 → H36 FAIL）。

### 二、UTF-8 BOM 触发连锁假 FAIL

Windows 记事本 / Excel 导出的 UTF-8 默认带 BOM，BOM 会粘在首字段名前面变成 `\ufeffsubject_definitions`，六段式首字段认不出，于是 H1 报"缺字段"，接着 H20/H24/H27/H35 一起刷——**一份好稿看起来像废稿**。

- **修法**：`load()` 改用 `utf-8-sig` 读取，并对残留 BOM 兜底 `lstrip`。
- **新增用例**：`case25_bom_ok.md`（带 BOM 的正例，结果须与 case01 一致）。

### 三、全角冒号 `9：16` 与 `16x9` 写法漏检

中文输入法打出的全角冒号、以及口头常写的 `16x9`，原来都不匹配 `ASPECT_RE`。单个出现只是识别不到（退化成"未声明画幅"WARN），**但和半角写法混用时会被静默忽略，H14 混用检测直接失效**——段间换画幅这种必崩的错就漏过去了。

- **修法**：新增 `find_aspects()`，同时吃 `9:16` / `9：16` / `9 × 16` / `16x9`，统一归一化成半角 `a:b`；`x` 写法只认官方六档，避免把「3x3 网格」「1080x1920」误当画幅。
- **另加 WARN**：写法不规范时提示统一半角冒号（下游字符串匹配可能对不上），但不拦截。
- **新增用例**：`case26`（全角+半角混用 → FAIL）、`case27`（16x9 归一化 → 通过 + WARN）。

### 五、新增：文档自检脚本 + 可复制命令块

## v2.0.1（2026-11-01）· 审计修复（3 个真 bug）

v2.0.0 交付后做了一次全量审计，发现 3 个实打实的问题，全部修掉并补了回归用例。

### 一、切分把单段稿误判成两段（**最严重**）

`split_multi_segments` 把 `subject_definitions` 与 `integrated_multimodal_description` **都**当段起点。这两个是同一段里的不同字段，所以任何完整单段稿都会被切成 2 段——**剥壳后的 `.txt` 尤其必然中招**（它正是"字段名纯文本独占一行"，两行都命中）。后果是每段都缺字段，刷出一堆假 FAIL，用户会以为稿子废了。

- **修法**：先在两类字段里选出现次数多的那个当**唯一**锚点；两类都不超过 1 次 ⇒ 单段。
- **验证**：单段 `.md` / 载荷 `.json` / 剥壳 `.txt` 全部判 1 段；四段合稿仍正确判 4 段。
- **防复发**：新增 `case24_stripped_single_seg_ok.md`（剥壳单段稿，结果须与 case01 一致）。

### 二、H34 被当成"图槽越界"检查，实际它只查跨段类型

`H34` 只比对**同一 `Picture N` 在不同段是人还是场景**，从不看 `Picture M` 是否超出 `images` 长度。v2.0.0 删掉 `doctor` 后，把这个职责错挂到了 H34 上（`delivery.md` / `checklist` B14、I61 / `gates` P0-23 四处），会让人以为跑了 lint 就查过越界了。

- **修法**：`load()` 现在读取载荷的 `images` / `image_urls` / `media` / `refs` 数组；新增 **H36 图槽越界**——
  - 正文最大 `Picture N` > 数组长度 → **FAIL**；
  - 槽位是空值/空串 → **FAIL**（空槽等同省图，槽位照样前移）；
  - `Picture` 编号不连续 → WARN。
  - 输入是剥壳 `.txt`（无 `images`）时不触发，不打扰纯文生稿。
- **文档同步**：`delivery.md §三`、`checklist` B14/I61、`gates` P0-23、`diagnose.md §十` 维度 1、`pipeline.md` G5 全部改成「H36 查越界 / H34 查跨段类型」，并注明**必须喂载荷 JSON 才触发 H36**。
- **新增用例**：`case22`（4 张图对齐 → 未越界）、`case23`（引用 Picture 4 只给 2 张 → 越界 FAIL）。

### 三、版本串残留

- `diagnose.md` 头部还写着「机检码 H1–H34」→ 改为 H1–H36。
- 全包 `H1–H35` → `H1–H36`，用例数 21 → 24。

### 自检结果

- `python -m py_compile scripts/h3_lint.py` 通过。
- **24 个用例 100% 零放水通过**（原 21 + 新增 3）。
- 四段合稿 `case18` 仍 0 FAIL / 0 WARN；多段下 H14「未声明画幅」只报一次（`（全片）`前缀），不按段刷屏。
